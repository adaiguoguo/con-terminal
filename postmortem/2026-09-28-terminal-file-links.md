# 终端文件链接被交给系统 URL 打开器

## 发生了什么

macOS 终端中 ⌘点击绝对路径、相对路径或带行列号的路径时，系统报无法打开应用（-50），文件没有在 Con 编辑器中打开。这与 #199 描述的编辑器集成缺失有关。

评审还发现两个边界问题：`README:20`、`Makefile:12:3` 会被 URL 解析器当作协议；首次创建编辑器时，光标已定位但目标行可能仍在视口外。

## 根因

Ghostty 的 OPEN_URL 事件也承载普通文件路径，Con 原来将非 OSC 8 的事件直接交给系统 URL 打开器，没有解析终端工作目录和源码位置。

无扩展名文件的名称符合 URL scheme 语法，仅凭 URL 解析成功不能判断目标类型。编辑器的滚动依赖正文布局尺寸，文件加载完成可能早于首次布局，而此前没有重试机制。

## 修复

- 按来源终端的 CWD 解析路径，处理行列号、路径规范化以及缺失文件、特殊节点和远程 file URL。
- 保留明确的 URL 协议；先检查实际存在的文件及位置后缀，再处理其他 URL。保留含冒号的真实文件名及 `mailto:`、`tel:` 等协议的行为。
- 文本在编辑器中打开，支持的图片使用现有预览，文档、目录、二进制及大文件使用正确编码的 file URL 交给系统。后台检查完整 UTF-8 和控制字节，读取上限为 8 MiB。
- 异步加载后应用行列号，复用已打开的未保存缓冲区，包括通过符号链接打开的文件；较早完成的请求不会覆盖较新的定位请求。字符列转换为 UTF-8 字节位置。
- 保留带请求代次的待滚动状态，正文获得有效布局尺寸后重试一次，并安排下一帧让列表消费滚动请求。零尺寸布局继续等待，过期请求失效。
- OSC 8 使用原有独立策略。

## 验证与范围

本轮 71 项相关测试全部通过，包括 3 项新增回归：无扩展名文件与真实协议的区分、首次布局及零尺寸/过期请求处理、真实 GPUI 布局后第 200 行位于可见区域。测试窗口没有平台帧循环，使用 GPUI 的 `simulate_next_frame` 驱动布局后安排的帧，并断言实际滚动偏移与视口位置。

其余回归覆盖图片、文档、目录、二进制、大小限制、URL 编码、特殊文件、Unicode 列、未保存缓冲区、请求顺序、Ghostty 输入/复制和 OSC 8。Unix socket 测试需要在解除沙箱绑定限制后运行。此前版本完成 macOS debug 构建及独立应用交互验证；本轮评审修复完成自动化验证，已更新独立测试应用并补充回归示例。用户验证发现裸文件名无法点击：解析器虽可处理 `README:20` 和 `Makefile:12:3`，Ghostty 默认检测规则并不匹配这些不带斜杠的文本，事件不会到达解析器。已将可点击示例改为 `./README:20` 和 `./Makefile:12:3`，并在示例中标注裸文件名限制。新增场景的真人点击验证尚未全部确认。未验证真实 PowerPoint 应用启动。

本补丁只解决 macOS 的文件打开与定位。裸文件名的识别、无效路径是否高亮仍由 Ghostty 检测逻辑决定，Windows/Linux 路径检测也不在范围内，因此仅关联 #199，不关闭该问题。

## 经验

OPEN_URL 事件名不能保证内容是 URL，需要结合文件系统与来源终端上下文路由。光标更新和滚动完成是两个阶段，首次布局竞态应通过实际视口断言验证。
